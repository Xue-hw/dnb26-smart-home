# 智能家居整合与运行说明

本次系统由香橙派运行 FastAPI、MySQL、Nginx、目标识别及人脸服务，网页和 Android APK 访问相同的 HTTP API。已交付 Arduino 保留两扇门、灯光和风扇执行及温湿度、光照采集职责。双 UNO 通过电脑 USB 网关与香橙派交换命令和状态；当前已部署的硬件模式为真实 `gateway`。

本地新增整合固件、电脑网关及实际硬件扩展，详细规则见 [硬件整合说明](hardware-integration.md)。本轮已完成烧录与部署，Web/新 APK 版本为 2.1.0；旧 APK 需要覆盖升级，手机端按联调表复验。窗户、雨滴、烟雾、空调和独立锁在真实网关模式隐藏，通用代码及原始资料保留。

## 识别与门禁流程

摄像头只有一个采集所有者。物体识别和人脸识别各有独立的最新帧消费线程，避免互相排队；缓存有界，不积压整个视频。物体和人脸结果带各自的帧编号与采集时间，GUI 分别检查新鲜度。

自定义目标模型负责无人机、灭火器和灯泡，COCO 通用 YOLO11n 提供人、车等 80 类目标。同一帧依次运行两个目标模型，使用模型锁避免多请求同时复用设备缓冲。CPU `.pt` 和 Ascend `.om` 均可通过配置选择；OM 旁边需有同名 JSON 类别元数据。模型加载或推理失败会显示离线状态并报警。

当前启用代码版本为 `integration-20261116-v210-uno-r3`（前端 2.1.0，真实双 UNO 网关后端），自定义模型为 `shared/models/custom3_640.om`，通用模型为 `shared/models/general640.om`，两者均实际使用 Ascend NPU。线上目标识别置信度配置为 `0.5`。原双类 NPU 模型、三类 CPU 权重及旧配置均保留，便于人工回退。

三类训练、验证及数据限制见 `docs/bulb-model-training.md`。板端另对 35 张标注图片做了置信度 0.5、IoU 0.5 的固定工作点检查：灯泡 33 张、51 框，TP=23、FP=7、FN=28，Precision=0.7667、Recall=0.4510；另外各一张无人机、灭火器样例分别正确匹配 1 框、2 框。三类模型平均耗时 48.09 毫秒（含预后处理）；此小样本检查用于确认 OM 可运行，不替代完整验证集的 mAP。

人脸注册使用组员交付的照片重新提取 128 维 `.npy` 特征。运行服务不加载交付的 `known_faces.pkl`。身份匹配阈值默认 `0.45`，由 `DNB_FACE_TOLERANCE` 配置。人脸注册和推理输入长边最多 800 像素，避免大照片使 HOG 长时间占用计算；原图保留用于归档，识别框映射回原图坐标，当前 `640×480` 实时画面保留原分辨率。实时人脸、上传验证和注册共用原生模型的推理互斥锁，防止同时调用共享 HOG/encoder；目标识别仍独立使用 NPU。

实时门禁必须满足：画面只有一个授权人脸，同一会话先睁眼、连续闭眼至少两次采样、再睁眼，且当前图像来自仍在线的实时采集会话。换人、多人、离开、采样间隔过大、超时、摄像头断开或重连均使会话失效。派发前再次检查授权记录和单调采集时间，超过 1.5 秒的图像不能触发门禁或灯光。

上传照片和本地录像可以识别物体与身份，但始终不能获得现场眨眼通行资格，也不触发硬件联动。眨眼属于课程原型的基础活体判断，仍需要现场验证采样速度、光照和阈值。

界面区分身份匹配、眨眼通过、通行资格、命令回执和门的控制器状态。控制器 `ACK` 表示处理了命令；本次双 UNO 没有门磁或限位反馈，`state_basis=actuator` 的遥测仅表示舵机控制状态，物理位置需要现场确认。当前硬件 `mock` 下的 ACK 明确标为模拟回执。

## SQL 与持久数据

保留 `integrations/database/smarthome_setup_v2.sql` 和组员的四张原表：`authorized_users`、`device_current_status`、`system_history_logs`、`security_vision_logs`。整合后端在同一 MySQL 中补充 `dnb_*` 表，用于多字段状态、人员编号、幂等命令、完整事件、报警和设置；不转为 SQLite，也不在数据库故障时回退内存数据。

人员删除会停用授权。启动时导入交付照片会检查包括停用者在内的现有记录，不能把撤销的授权自动恢复。原 SQL 的精确示例占位用户在初始化时停用；真实注册资料保留。

设备状态按本次上报字段合并，历史只记录实际收到的新采样。每种传感器指标显示自己的采样时间；收到光照更新不会把旧温度伪装成新采样。门开启时间单独保存，周期性上报 `open` 不会重置门未关报警计时。

识别照片和临时 JPG 按保留天数清理，默认 7 天。注册照片和人脸特征不参加照片保留期清理。`DELETE /api/temp/clear` 仅清理临时目录。

## 报警和联动

- 温度达到开启阈值启动风扇，达到或低于关闭阈值停止，默认 `30/28°C`，使用迟滞避免频繁切换。新增 `gateway` 模式由 UNO1 本地执行，后端只同步阈值和报警，手动模式持续生效。
- Mock 兼容逻辑保留烟雾报警、雨滴报警与自动关窗；实际交付未安装对应模块，双 UNO 真实模式隐藏这些入口。
- 同一实时输入连续三次识别灯泡可申请开灯，联动有冷却时间；照片和回放不能触发。
- 摄像头连续 5 秒没有新画面即离线并清除缓存；Arduino 串口心跳超时会离线，未接入时不伪造设备反馈。
- 门长时间未关、模型不可用和磁盘不足 1 GB 会报警。使用 NPU 时另外查询 `npu-smi` 健康告警。
- 确认报警表示已经阅读，故障是否恢复单独记录。

## 板端部署目录和操作

项目路径：`/home/HwHiAiUser/projects/dnb26-smart-home`。

| 目录 | 内容 |
| --- | --- |
| `releases/<版本>/` | 后端、部署脚本、GUI 静态构建及原始 SQL 的代码版本 |
| `current` | 当前启用版本的软链接 |
| `.venv/` | 独立 ARM64 / Python 3.10 推理环境 |
| `runtime/` | 在用户目录解包的 MySQL、Nginx 和运行库 |
| `shared/models/` | 模型与人脸关键点权重，跨版本保留 |
| `shared/mysql/` | MySQL 数据文件 |
| `shared/data/` | 识别归档、人员照片与 `.npy` 特征 |
| `shared/app.env` | 私有运行配置，权限 `600` |
| `shared/credentials.json` | 随机生成的数据库密码和管理员令牌，权限 `600` |
| `shared/*-service.log` | 用户服务日志 |
| `shared/verification.json` | 真实接口测试产生的检查结果，不含密码 |

```bash
systemctl --user status dnb26-mysql dnb26-api dnb26-web
systemctl --user restart dnb26-api dnb26-web
tail -n 80 ~/projects/dnb26-smart-home/shared/api-service.log
```

更新代码先在 PC 构建同源 Web，然后执行：

```powershell
.\.venv\Scripts\python.exe deploy\deploy_system.py --release <唯一版本名> --activate
```

不加 `--activate` 的后续部署只传输代码，不切换线上版本。`current` 使用软链接原子替换。重启后仍需检查 API 状态和日志，部署脚本不会声称已经完成识别验证。回退时将 `current` 指向保留版本并重启 API/Web；`shared/` 中的 MySQL 数据和模型不随代码回退。

```bash
~/projects/dnb26-smart-home/.venv/bin/python \
  ~/projects/dnb26-smart-home/current/deploy/verify_edge.py \
  --root ~/projects/dnb26-smart-home --exercise
```

该命令的写入测试仅允许显式 `mock` 硬件模式，验证后恢复温控设置、模拟温湿度以及关闭的门灯状态。实机串口模式下只能运行不带 `--exercise` 的识别与状态检查。

Arduino 接线、驱动固件、传感器数值方向及门窗到位开关需与硬件组确认，再把 `DNB_HARDWARE_MODE` 从 `mock` 改为 `serial` 并配置实际串口。协议示例见 `backend/README.md`。公网访问和可信 HTTPS 还需要实际可达的域名、VPN 或校内网络入口；当前没有创建付费服务或公网端点。
