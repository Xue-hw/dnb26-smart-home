## 一、项目概述与团队分工

### 1.1 项目目标与完成内容

本项目面向北京邮电大学国际学院 Design and Build 工程实践课程，围绕智能家居原型完成环境监测、设备控制、视觉识别和门禁交互。软件组承担香橙派 AIpro 边缘服务、YOLO 目标模型训练、人脸识别、Web 与 Android 图形界面，以及与双 Arduino UNO 的通信联调，将摄像头、数据库、用户操作与实体执行器接入同一业务流程。

软件系统以香橙派为运行中心，电脑承担模型训练、前端构建和 USB 网关转发。摄像头直接接入香橙派，YOLO 和人脸服务从共享视频输入获取图像；FastAPI 统一处理识别、人员授权、历史查询和控制命令，MySQL 保存业务数据。电脑网页与手机 APK 访问同一后端，设备动作通过电脑网关送达对应 UNO，执行回执和遥测再返回双端界面。[1][2]

## 二、系统设计

### 2.1 本地与板端协同架构

系统按计算任务和设备连接方式分配职责。Windows 电脑使用 GPU 训练模型，完成 GUI 构建，并保持与两块 UNO 的 USB 串口连接；香橙派集中运行摄像头采集、视觉推理和业务服务。两端通过局域网交换结构化数据，避免把模型训练负载放入板端实时服务。

### 2.2 图像、命令与数据的处理关系

摄像头由单个采集服务管理，物体识别与人脸识别分别消费最新帧。两条识别流程具有独立结果时间和帧编号；人脸处理较慢时，目标检测仍可继续更新。缓存只保留有界的近期数据，控制动作在派发前再次检查图像时效和采集会话，防止旧画面触发设备。

用户控制采用命令记录驱动：后端生成命令编号并保存请求，网关领取后转为串口指令，收到 UNO 回执后更新命令结果。遥测负责刷新设备状态，事件负责记录动作与触发来源。界面据此分别显示请求受理、控制器确认和设备反馈，便于定位网络、串口与执行器之间的问题。[2][7]

### 2.3 数据库设计

数据库沿用组员提供的 authorized_users、device_current_status、system_history_logs 和 security_vision_logs 四张原表，整合后增加 dnb_* 业务表，保存多字段状态、人员编号、幂等命令、报警与设置。传感器按实际收到的字段合并，每项指标保留自己的采样时间；光照更新不会刷新旧温度的时间戳。数据库异常通过服务状态和报警暴露，恢复后继续读取真实记录。

用户服务结合 linger 设置支持退出 SSH 后继续运行，冷启动恢复和电脑网关停启分别验证。板端通过局域网向电脑 Windows Time 获取 NTP 时间，时间同步独立于手机热点入口。5 次只读 HTTP 采样中，最小往返样本估计板端相对电脑偏差约 0.004 秒，中位偏差约 0.014 秒。这组结果反映该次局域网测量；眨眼会话和图像时效判断仍使用单调时钟，避免系统校时改变动作时序。[8]

## 四、YOLO 目标识别模型训练

### 4.1 模型分工与类别设计

目标识别采用两个独立模型。COCO 通用 YOLO11n 负责 person、car 等通用类别，自定义 YOLO11n 负责 drone、fire_extinguisher 和 light_bulb。两个模型对同一输入帧依次推理，结果保留模型来源后合并显示，避免将自定义类别编号解释为 COCO 类别。项目先训练无人机与灭火器双类模型，再扩展灯泡类别以支持视觉开灯。

### 4.2 数据集构建与质量控制

| 数据来源 | 训练图片 | 验证图片 | 灯泡留出测试 |
| --- | --- | --- | --- |
| 原无人机、灭火器数据（去重后） | 3,748 | 690 | 0 |
| 新增 Open Images 灯泡数据 | 215 | 46 | 33 |
| 初始三类数据集合计 | 3,963 | 736 | 33 |

灯泡采用 Open Images 官方人工边界框标注，类别标识为 /m/0h8l4fh。构建脚本从固定范围的标注文件中抽样，排除成组目标和描绘类标记，并保存图像来源、划分与哈希。图像按解码像素 SHA256 去除完全重复，灯泡图再按 64 位 dHash 相似性分组，同组保持同一划分。旧数据使用硬链接复用图片，三类标签独立保存，原数据目录继续保留。[3]

### 4.3 训练环境与参数

训练在 RTX 4060 Laptop GPU 8 GiB 上运行，独立环境使用 Python 3.12.13、PyTorch 2.7.1+cu128、torchvision 0.22.1+cu128 和 Ultralytics 8.4.89。初始三类模型从双类最佳权重初始化，使用 AdamW、随机种子 26、640 像素输入、batch 8，共完成 30 轮训练。Windows 多进程加载发生内存分配异常后，从 last.pt 恢复并将 workers 设为 0，训练恢复记录和权重校验值写入元数据。

### 4.4 评估口径

验证集用于模型比较，33 张灯泡图片用于补充留出评估。旧类原始数据存在重复和相似场景，候选又从旧模型初始化，因此旧类结果按相同验证集的配对比较解释。灯泡留出集只覆盖新增灯泡类别。训练验证指标、固定阈值检测计数和摄像头演示分别记录，三者各自回答模型质量、部署工作点和业务联动问题。

## 四、YOLO 训练结果与部署评估

### 4.5 初始三类模型验证结果

| 类别 | Precision | Recall | mAP50 | mAP50-95 |
| --- | --- | --- | --- | --- |
| 无人机 | 0.9130 | 0.7560 | 0.8356 | 0.4034 |
| 灭火器 | 0.8761 | 0.8667 | 0.8990 | 0.6243 |
| 灯泡 | 0.6312 | 0.4966 | 0.5208 | 0.2827 |
| 三类平均 | 0.8068 | 0.7064 | 0.7518 | 0.4368 |

上述结果来自 736 张三类验证图片、640 像素输入。Precision 表示预测目标中的正确比例，Recall 表示标注目标被检出的比例；mAP50 为交并比阈值 0.50 下的平均精度均值，mAP50-95 为多个交并比阈值下的平均结果。33 张、51 框灯泡留出测试的 Precision、Recall、mAP50 和 mAP50-95 分别为 0.6665、0.5294、0.5727 和 0.3007。[3]

### 4.6 针对耳朵与眼镜误检的再训练

实景联调暴露了耳朵和眼镜被高分识别为灯泡的问题。再训练从原训练集挖掘误检候选，经图像核对选取非灯泡负样本，并从同一公开训练场景裁出两张无旧目标的局部区域，衍生图只加入训练集，训练图片增至 3,965 张。训练没有使用登记照片或新增现场人物画面。run-v4 完成 10 轮后早停，最终依据验证集工作点规则选择第 10 轮检查点。[4]

| 比较项目 | 再训练前 | 第 10 轮模型 |
| --- | --- | --- |
| 灯泡验证集 TP / FP / FN（阈值 0.70） | 27 / 3 / 122 | 28 / 2 / 121 |
| 灯泡测试集 TP / FP / FN（阈值 0.70） | 18 / 3 / 33 | 21 / 0 / 30 |
| 三类平均 mAP50-95 | 0.4368 | 0.4325 |
| 无人机验证 TP（阈值 0.70） | 321 | 305 |

TP、FP、FN 分别指正确检出、误检和漏检数量。再训练减少了该固定工作点的灯泡误检，同时无人机检出数和三类平均 mAP 出现下降；阈值 0.50 的灯泡验证计数也未改善。测试集已在前期评估中使用，后续比较用于描述模型变化。原耳朵、眼镜场景的双端复验确认不再出现原误识别。

### 4.7 ONNX 导出与 Ascend NPU 推理

模型由 PT 导出为 ONNX，再经 ATC 编译为 Ascend310B4 的 OM，类别信息使用同名 JSON 保存。初始 ONNX 输入为 [1,3,640,640]，输出为 [1,7,8400]，图检查和确定性输入数值比较通过。第 10 轮 OM 在 35 张标注图片、置信度 0.70 与 IoU 0.50 下得到灯泡 TP=21、FP=0、FN=30；平均检测耗时 51.56 毫秒，包含预后处理、不含读图。该耗时对应单模型图片检查。[3][4]

## 五、人脸识别与眨眼门禁

### 5.1 人员注册与身份匹配

人员管理将姓名、人员编号、注册照片和人脸特征关联保存。注册要求照片包含一张清晰人脸，服务提取 128 维特征并保存为 .npy，读取时检查向量形状与有限值。运行服务使用重新提取的特征，不直接加载交付的 pickle 文件；人员停用后撤销授权，重新导入资料时保留停用记录。[5]

身份识别使用 HOG 定位人脸，再计算与授权特征的欧氏距离，选择距离最小的对象。界面匹配分数定义为 1 减去该距离，匹配门限 0.65 对应距离上限 0.35。这个分数是特征距离的显示变换，不能解释为统计意义的身份正确概率。输入长边限制在 800 像素内，框坐标映射回原图；注册、上传验证与实时分析共用原生推理互斥锁。

### 5.2 低帧率下的眨眼会话

图 5-1 身份匹配、眨眼核验与门控制反馈流程

眨眼通过 68 点关键点中的双眼区域计算 EAR，EAR 表示眼睛纵向距离与横向宽度的比值。会话先记录睁眼，再检测 EAR 低于 0.23 的闭眼采样，最后确认重新睁眼。针对板端处理帧率较低的情况，闭眼条件调整为至少一个处理帧，验证窗口固定为 15 秒，相邻采样间隔上限为 1.5 秒。

首次匹配的实时特征作为固定锚点，维持同一人在短时分数波动下的眨眼连续性；派发动作仍要求该帧匹配授权身份。多人、换人、无人脸、超时和采集会话变化会清除会话。上传照片及本地录像可进行身份分析，控制链只接受新鲜实时输入。真人测试确认已登记本人眨眼后实物开门并自动关闭；一名未登记者被拒绝，静态上传与屏幕照片测试未产生通行。[5][9]

### 5.3 单次通行与门周期冷却

通行冷却由独立状态机管理，关联命令编号，并等待本轮门开启后再收到关闭反馈才释放。相机重新连接或人脸会话重建不会直接解除门周期冷却。门反馈采用执行器控制状态；机械位置的进一步验证需要门磁或限位传感器参与。

## 六、双端交互与数据一致性

### 6.3 命令状态与双向同步

设备操作先产生 pending 命令，收到控制器确认后显示 acked；失败和超时分别显示 failed 与 timeout。等待期间限制重复提交，超时后保留结果未知提示。前端查询后端设备状态，不在按钮点击时直接改写为已执行，电脑操作后手机可以从同一数据库观察结果，手机反向操作也按相同流程回传。

设备按 board_id 绑定 UNO，所属板离线时禁用对应控制，另一块板的设备继续独立显示。车库门运动期间限制重复切换。亮度、RGB 颜色、灯珠数、风速和自动模式通过 capabilities 决定入口；真实网关只展示实际安装的设备，窗户等装饰元素与可控设备分开呈现。[6][7]

### 6.4 视频、照片与识别结果

实时画面采用 MJPEG，识别结果由独立接口提供帧号与时间。人脸和物体结果分别校验新鲜度，网络异常或帧过期时撤下旧的通行信息。APK 针对 WebView 跨来源媒体访问使用 fetch 获取 Blob，再生成本地 URL 展示，处理读取超时、请求取消和组件卸载时的资源释放。抓拍区根据后端 saved 与 archive_url 回执展示保存结果。

### 6.5 历史查询与权限保存

历史页支持传感器曲线以及设备、识别事件查询，事件每页 20 条。正在编辑的筛选条件与已执行的查询条件分别保存，翻页沿用上次成功查询的条件，迟到响应不能覆盖新查询。时间输入按客户端时区显示，接口使用统一时间范围；固定区间测试验证两端的记录、分页与空结果一致。

查看状态和历史采用只读入口，控制设备、修改人员与保存配置需要管理员授权。令牌经请求头传输；选择记住权限时，Web 使用服务端会话与 Cookie，Android 使用 Keystore 支持的加密保存。退出授权会清除已保存权限。门密码采用掩码输入，确认后清空，界面与日志避免回显密码。[10]

### 6.6 双端工程验证

前端完成 TypeScript 检查、ESLint、构建和完整回归，覆盖命令、刷新、权限恢复、媒体、图片拖放与人员录入。共享界面在 1440、768、390 和 320 像素宽度下逐页检查，共 24 组布局验证，覆盖横向溢出、按钮裁剪、导航可达性和键盘焦点。实体 APK 另行核对安装版本、签名、包哈希和重开后连接恢复。[6][11]

## 七、软硬件接口与通信联调

### 7.1 双 UNO 与电脑网关

UNO1 负责室内温湿度、光照、灯带、风扇、键盘、OLED 与入户门；UNO2 负责 RFID 与车库门。两块板通过 9600 bps USB 串口接入电脑网关，网关经局域网调用 POST /api/hardware/gateway/exchange，与香橙派交换遥测、事件、回执和待执行命令。网关以身份握手核对板卡，设备归属与串口端口分别管理。[7]

### 7.2 DNB1 协议与命令映射

下行指令包含 DNB1 前缀、32 位十六进制命令编号、操作码和参数；上行以 DNB1 开头的 JSON 行区分 identity、state、ack 与 event。后端把统一的设备动作转换为各板操作码，并将板端字段转换为 GUI 使用的设备与传感器模型。

| 操作类别 | 主要操作码 | 软件侧处理 |
| --- | --- | --- |
| 双门控制 | DOOR_OPEN / DOOR_CLOSE | 按门编号选择 UNO，关联回执及开关状态 |
| 灯光控制 | LIGHT_ON / OFF / AUTO<br>BRIGHTNESS / LAMP_RGB / LAMP_COUNT | 校验亮度、RGB 与 1～8 颗灯珠参数 |
| 风扇控制 | FAN_ON / OFF / AUTO / FAN_SPEED | 转换开关、自动模式和 0～100% 转速 |
| 温控配置 | TEMP_LIMITS | 区分后端期望阈值与 UNO1 实际阈值 |
| 扩展设置 | ENTRANCE_PIN / GARAGE_PIN<br>VOICE_ENABLE | 校验参数、保护敏感字段、关联确认结果 |

### 7.3 命令队列与断线恢复

每次网关启动建立独立 Session UUID，串口重连使用新的 Connection ID。每块板同一时刻只保留一条等待确认的派发命令，相邻指令间隔至少 1.1 秒；普通命令有效期为 5 秒，视觉触发动作还受 1.5 秒图像时效限制。已领取命令不因 HTTP 响应丢失而重新派发，重连后过期动作失效。板卡分别检查心跳，超过 10 秒缺少更新按离线处理。

温控由 UNO1 本地执行，软件同步默认 30°C 开启、28°C 关闭的迟滞阈值，避免后端重复调度。灯泡联动要求连续三次可信实时检测，设置冷却并通过命令回执推进灯效，最终采用青色常亮、80% 亮度并保留灯珠数。上传图片用于识别分析，硬件联动只接收实时输入。[2][7]

## 九、典型问题与工程处理

### 9.1 手机与电脑网络路径差异

联调中，电脑能访问香橙派并不保证手机具有相同路由。工程排查先使用手机浏览器检查状态接口，再验证 APK。手机经热点访问电脑转发入口，由电脑转至板端服务；应用保存后端地址和网络模式，覆盖安装后核对重开恢复。将网络可达性、应用请求和业务控制逐层验证，使连接问题可以定位到实际环节。

### 9.2 WebView 视频与照片访问

浏览器可显示的媒体 URL 在 Android WebView 中出现过访问失败。处理时将视频和照片获取纳入共用媒体服务，使用 Blob URL 展示，并增加请求取消、15 秒读取超时与卸载清理。修复后分别复验连续动态画面和抓拍预览，避免只验证接口返回成功。

### 9.3 低帧率造成眨眼漏采

人脸编码较慢时，连续两个处理帧闭眼的要求容易漏掉自然眨眼。软件将闭眼采样调整为一个处理帧，同时保留睁眼先后顺序、固定 15 秒窗口和实时特征锚点；每次提交开门前再核对当前身份与图像时效。这样把采样适配放在人脸会话内部，保持上传照片与控制链的输入边界。

### 9.4 误检样本驱动模型再训练

灯泡高分误检说明单纯提高阈值不能覆盖所有背景。软件从既有公开训练数据中筛选困难负样本，并把局部裁剪与来源记录一并保存。检查点选择依据验证集工作点，保留旧类别召回和 mAP 的变化。复验既检查灯泡正向识别，也回到原耳朵、眼镜场景观察误检，使训练变化能够对应到现场问题。

### 9.5 串口拥塞与过期命令

双端连续操作会把短时间请求集中到串口。网关通过按板串行派发、1.1 秒节流与命令有效期控制，减少等待确认指令的堆积；会话编号和连接编号用于隔离重启前后的动作。命令超时保持独立记录，后续成功回执不会改写先前记录，便于根据命令编号继续分析通信可靠性。

### 9.6 板端时间与历史查询

板端时间偏差会影响采样排序和历史区间。软件将动作时效建立在单调时钟上，GUI 使用服务端时间与本地经过时间校验新鲜度，再以局域网 NTP 修正墙上时钟。历史记录保留原采样时间，校时后新采样继续写入，避免修改旧记录来掩盖时间差异。[4][8][9]

## 十、工程特点与成果分析

### 10.1 视觉识别到设备执行的完整链路

本项目把模型输出接入了可追踪的控制流程。灯泡检测经过连续确认、时效检查和冷却后生成设备命令；人脸通行经过身份、眨眼与门周期判断后派发开门。模型结果、命令编号、回执和遥测分别保存，使视觉能力能够落实到房屋原型的灯光与门禁交互。

### 10.2 训练、部署与现场问题相互验证

模型工程包含数据来源、去重审计、训练恢复、验证指标、检查点筛选、格式转换和 NPU 检查。耳朵与眼镜误检进入负样本再训练流程，再训练结果同时呈现灯泡工作点变化与旧类代价。这个过程形成了从现场现象到可复现实验、再到实物复验的工程闭环。

### 10.3 双端共用业务与分布式控制

网页与 Android 共享前端源码，统一读取香橙派数据库；两块 UNO 保留本地温控和门动作时序，电脑网关处理串口和局域网交换。该分工使界面布局、模型推理与底层实时动作分别演进，设备能力通过接口显式声明，减少前端对具体接线和固件细节的依赖。

### 10.4 资源投入与运行组织

训练复用电脑 GPU，边缘推理使用香橙派，软件工程采用开放工具链。训练环境、服务环境与运行数据分离，代码更新保留数据库和人员资料，旧权重与版本可用于回退。报告对软件资源以设备和运行职责说明，采购成本随实际设备及授权清单核算。

### 10.5 项目总结

软件组完成了香橙派边缘服务、YOLO 训练与 NPU 部署、人脸眨眼门禁、Web/Android 共用界面，以及双 UNO 通信联调。系统能够采集和保存环境数据，识别通用与自定义目标，管理授权人员，并将双端操作和视觉触发传递至实体设备。训练与联调记录为模型效果、交互结果和工程问题提供了可核查依据。

## 十一、项目展望

后续拟围绕智能交互、视觉性能与多端协同扩展系统，通过完整链路的时延与资源测量定位瓶颈，逐项评估优化效果。

### 11.1 接入 AI API 与自然语言交互

在后端增加 AI API 适配层，接入云端或本地模型，为 GUI 提供自然语言设备查询、历史数据解释和场景控制建议。用户意图转换为结构化请求后，经既有权限校验、参数检查和命令流程执行。接口层管理超时、限流与失败提示，外部服务中断时保留局域网监测与基本控制。

### 11.2 优化模型与端侧推理性能

分阶段测量采集、预处理、推理、后处理和编码耗时，评估输入分辨率、检测区域与推理频率。模型侧研究轻量化、剪枝和知识蒸馏，在设备支持范围内评估精度转换与量化；运行侧复用缓冲区，减少格式转换和数据拷贝。采用同一评估集比较 Precision、Recall、mAP、时延和内存，确定精度与速度的取舍。

### 11.3 调整 CPU 与 NPU 算力分配

分析摄像头、双目标模型、人脸分析和 API 的资源占用，评估 CPU 预后处理与 NPU 推理的异步流水线。通过有界队列、任务优先级和按需调度，减少重复识别与过期帧处理，按画面变化调整检测频率。评估适合板端加速的人脸模型，平衡目标识别与门禁响应，持续观察利用率、内存、温度和功耗。

### 11.4 优化通信与控制链路

评估长连接事件推送或 MQTT 发布订阅，减少轮询与重复传输；遥测采用变化增量与周期全量快照结合，控制命令独立排队。串口侧通过误码率和稳定性测试评估更高波特率，精简重复字段。保留命令编号、有效期、去重与回执机制，统计控制时延、超时比例、通信流量和重连恢复时间。

### 11.5 完善双端状态同步与运行维护

以状态版本号或事件序号核对双端同步位置，重连发现缺失时获取全量快照。分别管理期望状态、控制器反馈和采样时间，避免旧消息覆盖新结果。完善可信 HTTPS、照片清理、低存储处理与依赖定向升级，使用结构化日志关联识别帧、命令和回执；结合供电与驱动信息分析 NPU 电流检测告警。

### 11.6 扩展场景数据与物理反馈

补充不同视角、距离、光照与遮挡样本，扩充灯泡困难负样本，按独立场景评估泛化。人脸门禁扩展授权人数和呈现攻击测试，统计误接受、误拒绝与通行时延，评估时序活体模型。硬件增加门磁、限位与风扇测速，将控制状态扩展为位置和转速反馈，为故障定位提供直接依据。
